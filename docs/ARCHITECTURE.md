# Housie Salesforce architecture

## Storage allocation

- `Housie_Account__c`: human account/profile and current account-wallet projection. Created only by an authenticated platform operator through Apex permission `HOUSIE_SUPER_ADMIN`.
- `Housie_Operation_Lock__c`: singleton infrastructure row (`Lock_Key__c=GLOBAL`) used by selected DML-only preparation/finalization transactions.
- 15 Big Objects: the 15 non-account logical entities in `docs/DATA_MODEL.md`.
- `Operation_Journal__b`: technical Big Object commit journal. This is infrastructure metadata, not a product entity.
- `Housie_Game_Command_Lock__c` and `Housie_Ticket_Command__c`: standard-object coordination/outbox records for the ticket purchase and withdrawal command flow.

All Big Object writes use `Database.insertImmediate()`. IDs are generated by Apex as 32-character lowercase hex values. Composite primary indexes are declared in metadata and must not be changed after deployment.

## Transaction and consistency boundaries

Big Object writes are non-transactional and are not atomic with ordinary Salesforce DML. The writer in `HousieOperationService.executeOperation()` performs Big Object writes only:

1. Write an operation journal row with status `PENDING`.
2. Write the operation's Big Object records.
3. Write the same journal key with status `COMMITTED` last.

Application reads must accept only records whose operation journal is `COMMITTED`. If a write fails before the final marker, the operation remains invisible to committed-record readers, but physical Big Object rows may already exist. This is fail-closed visibility, not rollback or native multi-record atomicity.

**The Big Object writer does not acquire the standard-object infrastructure lock.** Salesforce releases ordinary `FOR UPDATE` locks when `insertImmediate()` is invoked, so that lock cannot serialize the Big Object write sequence. Callers must not hold standard-object row locks when invoking the writer. The writer itself does not provide cross-request serialization or generic idempotency.

The infrastructure lock is used only in selected DML-only preparation/finalization transactions. Ticket purchase and WAITING-game withdrawal additionally use a durable per-game command gate: the prepare transaction reserves the command slot, the separate Big Object persistence request writes the operation, and the completion transaction finalizes the command and releases the gate. Do not generalize this ticket-specific gate into a claim that every business operation is serialized.

The operation journal currently has no scheduled repair worker. `HousieScheduler.execute()` is only a heartbeat. Prepared ticket commands can be surfaced and retried through the Board Hub flow, but that is not a general repair mechanism for every PENDING journal or stale command gate. Recovery is an explicit unfinished milestone.

## Account identity

The account key is a 32-character opaque random token, not a Salesforce record ID. It is currently also the URL context token for the initial shell. This is not sufficient authentication by itself for a public deployment: implement a separately authenticated invitation/session flow with expiry, revocation, replay protections and rate limiting before enabling public account-specific actions. The current resolver only resolves active account context.

## Game execution status

`HousieGameService.submitCommand()` currently records a `COMMAND_RECEIVED` event. It is not a game action processor. There is no implemented start-approval/capture flow, number-calling engine, marking engine, claim processor or settlement engine. The developer simulation controller writes simulation audit records; its accepted scenario names do not mean those product actions are implemented.

## Experience Cloud

Big Objects have no standard record detail pages, list views, sharing rules or OOTB UI. The custom `Housie_Account__c` record can use standard Experience Builder record detail components for profile/account context, but that page does not automatically render Big Object-backed boards, tickets or games. Those remain custom LWC/Apex experiences. The included `housieApp` LWC is the application shell; build the remaining domain screens as LWCs calling Apex controllers. ExperienceBundle/site activation is org-specific and must be completed in Experience Builder after deployment.
